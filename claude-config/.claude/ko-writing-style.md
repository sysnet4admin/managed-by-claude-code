# 한국어 작성 세부 규칙

`CLAUDE.md`의 "전역 한국어 작성 규칙"이 참조하는 상세 체크리스트다. 모든 프로젝트의 한국어
산출물(문서, 커밋 메시지, 블로그, 교안, 슬라이드 등)에 적용한다. 새로 발견한 어색한 표현은
이 파일에 바로 추가한다.

## 1. 번역체 표현 회피

- "거동은" → "동작은", "결과는", "양상은"
- "~의 뼈대"(spine 직역이면 "척추"가 아니라 "뼈대")
- "같은 잣대로 나란히 비교한다"("가로비교"는 직역)
- "~만 다룬다", "~에 국한한다"("~에 한정한다" 대신)
- "자동으로 유리한 자리에 놓인다"("구조적으로 시각적 우위를 점한다" 대신)
- "자기 인식"("메타 인식/메타 인지" 대신)
- "어느 선을 넘으면"("임계점을 넘으면" 대신)
- "형태의 실패", "실패 양상"("실패 모드" 대신)
- "이 글에서는 ~", "여기서는 ~를 풀어봅니다"("이 글은 ~를 다룹니다" 대신)
- "이 문서에서는"("본 문서는" 대신)
- "채점 기준"("루브릭"은 학술 용어라 일반 IT 독자에게 낯섦)
- "표준에 합류하지 않은", "마지막까지 남은"("홀드아웃"은 일반 독자에게 안 통하는 외래어)
- 문서/파일이 "수명을 다한다"("낡는다" 대신)
- "당시 상황으로는 맞다"("역사적으로 정확" 대신)
- "도구마다 하나씩", "하나로 모인다/통합"("난립", "수렴" 대신, 지나친 문어체)
- "차이가 거의 없다"("평평하다" 대신)
- "일관성이 없다"("체계가 없다" 대신)
- "~보다 체계적으로/일관되게 높지 않다"("~을 웃돌지 않는다" 대신, 잘 안 쓰는 표현)
- "이전 버전(4.6)", "새로운 Sonnet 5"("구세대/신세대"로 소프트웨어 버전을 사람처럼 의인화하지 않는다)
- "이번에 측정한 범위는 ~까지입니다"("이번 측정이 답한 것은"처럼 추상 명사를 화자처럼 세우지 않는다)
- "써도 문제없다는 것을"("안심하고 써도 된다"는 감정을 인위적으로 부여하는 표현)

## 2. 명사 연쇄를 서술형으로 풀어쓰기

"외부 의존성 장애, 클러스터 밖 원인, 정답 복수" 같은 명사 나열 대신
"외부 의존성에서 발생한 장애. 원인이 클러스터 밖에 있고 정답이 여러 개"처럼 서술형으로 푼다.

소제목과 결론 문장도 같다. 관형절로 압축한 명사구 주어 대신 조건 흐름 문장으로
쓴다(2026-08-04 저자 판정): "관측 기능을 기본 구성으로 켜는 비용은 작다" →
"관측 기능을 사용해도 추가로 드는 자원은 매우 작다" / "netkit의 상시 비용 차이는
없다" → "netkit으로 바꿔도 상시 비용은 달라지지 않는다".

## 3. 정확성을 감각 표현보다 우선

- 자원 지표는 무엇의 양인지 명시한다(2026-08-04 저자 판정): "메모리를 크게
  바꾼다" → "메모리 사용량을 크게 바꾼다". "메모리가 달라진다/줄었다"처럼
  지표가 주어일 때 "사용량"을 붙인다. "메모리를 533MiB 더 쓴다"처럼 동사가
  양을 담고 있으면 그대로 둔다.

- 기술 설명에서 "조절한다", "보정한다", "가중치를 둔다" 같은 정확한 동사를 감각적 동사
  ("흔든다", "들어 올린다")로 바꾸지 않는다. 문체에 활기가 필요하면 동사가 아니라 문장 구조
  (짧고 긴 문장의 교차, 비유, 사례)로 푼다.
- 감정 과잉·과장 표현을 자제한다: "~기 일쑤입니다" → "~할 수도 있습니다", "더 나쁜 상황이
  됩니다" → 결과를 그대로 서술("~하게 됩니다"), "다행히" 같은 편집자 감정 개입도 뺀다.
  걱정·공포를 부풀리지 말고 중립적으로 쓴다.

## 4. 기술 용어는 현업 검색 표준어 우선, 없으면 음차

한국어 IT 현업에서 실제로 많이 쓰고 검색되는 표현을 쓴다. 마땅한 표준어가 없으면 직역하지
말고 영어 발음을 그대로 차용(음차)한다.

- "마이그레이션"(migration. "이식"은 어색)
- "설정 스니펫"(snippet. "raw config 탈출구"는 직역)
- "외부 인증"("외부 auth" 대신), "요청/응답"("req/resp" 대신)
- 이미 음차가 표준인 것은 유지: 세션 어피니티, 미러링, 카나리, 락인(lock-in 병기)
- 직역 금지 신호: "탈출구", "뭉개짐"(→ "합쳐짐") 같은 구어/직역
- "설치 방식"("설치 경로"는 install path 직역. 코드 경로 문맥의 "동기화 경로"도
  "동작"으로. 파일 경로, 네트워크 경로처럼 실제 경로일 때만 "경로", 2026-08-04 추가)

## 5. AI스러운 문장 4패턴 금지

한국어·영어 문서, 발표 원고, 블로그 모두 적용.

- **(a) 영어 직역체**: 사물 의인화, 한국에서 안 쓰는 관용구, 수동 어휘 중심.
  금지 예: "아무리 ~해도 지나치지 않다", "AI가 올라탈 바닥", "사다리의 두 칸", "적어 둔 노트",
  "평행 사례", "솔직한 토로였습니다", "이 모든 게 굴러가는 데는 두 가지 장치가 깔려 있습니다".
- **(b) 요약·단언 반복**: 매 단락마다 결론 선언. 금지 예: "한 마디로 말하면 이것입니다",
  "핵심은 3가지입니다", "이것이 정답입니다". 정말 필요할 때 한 번만.
- **(c) 평균 수렴 구조**: 글 맥락과 동떨어진 일상 비유, 무엇이든 3개로 묶는 습관, 장문·단문의
  기계적 교차로 만든 인위적 리듬. 금지 예: "여섯 가지 질문을 먼저 책상에 올려놓아 보시기를
  권합니다", "건너야 할 다리의 길이를 재는 일".
- **(d) 안 중요한 문장을 위한 선언문**: 거창하게 선언한 뒤 평범한 인용이 따라옴. 금지 예:
  "처음 든 생각은 이거였습니다", "발표를 시작하면서 했던 말이 있습니다".

## 6. AI가 즐겨 쓰는 상투적 동사·표현

단어 자체는 틀리지 않지만 AI 생성물에서 반복 등장해 "AI가 쓴 티"를 낸다.

- "드러납니다"(reveals) → "~에서 알 수 있습니다", "~때문입니다", 또는 사실을 직접 서술.

## 7. 문장부호

em dash("—")와 가운뎃점("·") 금지. 이모지 금지. 화살표 남용 금지.

## 8. 대화 답변 규칙 (채팅 응답에 적용, 2026-07-20 추가)

문서만이 아니라 Claude의 한국어 대화 답변에도 적용한다. 배경: 답변이 압축된 한자어와
긴 문장 때문에 이해하기 어렵다는 피드백.

- 결론을 먼저 한두 문장으로 말한다. 세부 설명은 그 뒤에 둔다.
- 한 문장에는 내용 하나만 담는다. 조건, 근거, 예외를 한 문장에 몰아넣지 않는다.
- 괄호 부연을 자제한다. 부연이 필요하면 다음 문장으로 풀어 쓴다.
- 쉬운 동사를 먼저 쓴다. "성립한다" 대신 "가능하다", "정합" 대신 "맞다",
  "표적" 대신 "확인할 대상", "재고" 대신 "다시 생각".
- 전문 용어와 영어 용어는 처음 나올 때 한 번 풀어 쓰고, 이후 같은 말로 통일한다.
- 굵은 글씨, 표, 목록을 남발하지 않는다. 짧은 답이면 문단으로 충분하다.
